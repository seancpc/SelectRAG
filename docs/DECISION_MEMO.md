# SelectRAG 架構決策備忘錄(Architecture Decision Memo)

> **文件定位**:本專案的核心交付物——「我們該用哪種 RAG 配置?」的實證回答。
> 格式承諾:每軸結論寫成 trade-off 而非冠軍;必含一個「最無聊但最穩」選項;
> 誠實區必寫「預期會贏但輸了的組合」。
> **狀態**:A / B / C 軸與 judge 第一階段結案(2026-09-18);D / E 軸範圍外(§5、§6 說明理由)。

---

## 0. 執行摘要(Executive Summary)

**約束**:一張 RTX 4090(24 GB)、繁體中文醫療公開文件 8,029 chunks(健保給付規定、藥品仿單、支付標準)、必須附出處。
問題不是「RAG 能不能做」,而是在這個預算下,檢索策略、推論引擎、數值格式三個軸各該選哪一格,以及每一格的代價是什麼。
全部結論來自同一份 100 題人工真值評測集(v1.2)與同一台機器的受控對照,一行指令可重跑。

**選哪個**(每軸一個推薦、一個最無聊但最穩):

| 軸 | 推薦 | 關鍵數字 | 最無聊但最穩 |
|---|---|---|---|
| A 檢索 | hybrid(BM25 + bge-m3,RRF)+ bge-reranker-v2-m3 | recall@10 0.903 → 0.973、recall@3 0.808 → 0.941;代價:單卡與生成共用時每題檢索 13 ms → 1501 ms(§2.7) | BM25 + 文件脈絡調參:零 GPU、每題 13 ms、recall@10 0.903 |
| B 引擎 | 先做 FP8,再談引擎 | vLLM vs TRT-LLM 差 ≤ 10%;FP8 ×1.4–1.7 | vLLM bf16:pip 一行、無需轉換 |
| C 格式 | vLLM + GPTQ-Int4(官方預量化) | 吞吐 ×2.36(1000 vs 424 tok/s)、權重 5.3 GiB、faithfulness 與 bf16 在 judge 下不可分辨 | 同上 vLLM bf16 |

三軸疊起來:單卡上「hybrid + reranker 檢索、vLLM 跑 GPTQ-Int4」是本專案的答案;比起最穩配置,多養一個向量索引、
一個 cross-encoder、一份量化權重,換到頭部命中率 +0.13 與生成吞吐 ×2.4。

**代價與邊界**(不寫在這裡的話上面的數字會誤導):①量化改變輸出——GPTQ 對 bf16 的逐字一致率只有 0.25,判斷「品質沒差」
靠的是 faithfulness judge,而 judge 在分層校準集上 κ 只有 0.488,只能當**四格式相對比較**用,不是絕對品質保證;
②W4 量化放大簡體字漂移(含簡體題數 bf16 2 → GPTQ 6),部署面向繁體使用者需後處理;③所有檢索數字為同一 100 題上的上界估計,
無 held-out;④TensorRT-LLM 載不了 HF 格式的 AWQ / GPTQ(格式綁引擎),NV-Embed-v2 與釘選的 transformers 不相容,兩者列誠實區;
⑤D 軸(RAG 範式)與 E 軸(fine-tune)刻意不做,範圍留給檢索與推論兩層。

## 1. 問題設定與評測方法

- **場景**:醫療公開文件問答(健保給付規定、藥品仿單、支付標準、公告),
  必須有出處——citation 正確性與檢索品質同權重
- **語料**:8,029 chunks(CSV 6,350 / PDF 1,660 / HTML 19),結構優先切塊 + 長度上限
- **評測**:100 題人工判定真值(v1-full100,hash bdea697a),凍結後改動需記錄;
  指標 recall@k / hit@k / MRR,一行指令可重跑(`python3 -m selectrag.runner <config> <run_id>`)
- **為什麼同時報 recall 與 hit**:真值集含等價 chunk 時 recall 被稀釋;
  hit@k 回答「答案是否被拿到」。兩者以不變量 hit == (recall > 0) 互鎖
- **評測集的已知限制(誠實揭露)**:候選窮舉以 BM25 多輪改寫查詢輔助,
  存在偏向詞面重疊的採樣偏差;dense 檢索找到的等價 chunk 若未入真值集,會被低估——
  A 軸後續實驗須人工抽驗 dense 的「錯誤」命中

## 2. A 軸:檢索策略選型

### 2.1 已完成:BM25 baseline 與文件脈絡對照(2026-09-01)

| 配置 | recall@10 | hit@10 | MRR | 備註 |
|---|---|---|---|---|
| BM25 純正文(控制組) | 0.829 | 0.860 | 0.714 | CJK bigram + ASCII 詞,純標準庫 |
| BM25 + doc_title + heading_path | **0.905** | **0.920** | 0.732 | 建索引 <1s,查詢 <1ms/題 |

**發現 1:chunk 正文常不含文件身分**。藥品仿單的藥名只在文件首行,切塊後的正文
(適應症、用法)完全不含藥名——「四環素對哪些微生物有效」的正解 chunk 裡沒有「四環素」
三個字。這是 baseline 漏檢的主導根因(佔漏檢題 3/5),把 doc_title 注入索引即修復大半。

**欄位拆分 ablation(2026-09-29,v1.2、預設 k1/b,`configs/bm25_{title,heading}_only_full100.yaml`)**:

| 索引欄位 | recall@10 | hit@10 | MRR |
|---|---|---|---|
| 純正文 | 0.817 | 0.860 | 0.724 |
| + doc_title | 0.856 | 0.880 | 0.726 |
| + heading_path | 0.832 | 0.870 | 0.719 |
| + 兩者 | 0.903 | 0.920 | 0.732 |

**發現 59(事實)**:doc_title 是較大的單一來源(+0.039 對 +0.015),與藥名診斷一致;兩者合用 +0.086,大於單項相加 +0.054,有正向交互作用。
heading_path 對增益的貢獻不可忽略:拿掉它 ctx 增益從 0.086 掉到 0.039,少了過半。所以 SOURCES 記載的缺陷(正文被誤判成標題,進索引但不進 context)確實可能造成部分「檢索看得到、模型看不到」的增益。
另:純正文 v1 為 0.829、v1.2 為 0.817(差 0.012,主要來自 v1 → v1.1 補真值),文章 #1 原本寫「v1.2 差異 ≤ 0.003」只對四個代表點成立,已更正。

**發現 2:代價是早段精度微損**(50 題時 recall@3 0.776→0.773)。文件脈絡讓同文件
chunk 間相似度上升,深層召回變好、頭部排序略糊——reranker 的預期用武之地。

**發現 3:BM25 的結構性弱點清單**(dense/hybrid 的預期增益來源):
- 中英詞彙鴻溝:「雌激素經皮貼片」查不到「Estradiol Transdermal Patch」
- 詞面重疊不足:「同意書如何處理」對不上「簽名黏貼於病歷表」
- 同義文件排擠:他牌同成分 chunk 擠不進 top-10

### 2.2 BM25 k1/b 網格調參(2026-09-01)

兩輪網格(粗 6×5 + 高原細化),100 題,目標 recall@10、MRR 決勝負;取高原區中點、不取邊界:

| 配置 | 參數 | recall@10 | hit@10 | MRR | vs 文獻預設(1.5/0.75) |
|---|---|---|---|---|---|
| 純正文(調參後) | k1=0.5, b=0.1 | 0.870 | 0.900 | 0.772 | recall +4.2 pts |
| +文件脈絡(調參後) | k1=0.7, b=0.5 | 0.905 | 0.920 | **0.808** | recall 持平,MRR +0.08 |

**發現 4:文獻預設在本語料上不是好預設**。b(長度正規化)是主要變因——本語料 chunk
長度已被建置參數約束(max_chars=800、CSV 列有界),再做長度懲罰反而傷害含完整條文的
長 chunk;中文 bigram 的詞頻雜訊也偏好低 k1(快速飽和)。ctx 版因文件脈絡拉長了索引
文本,對 b 的容忍度較高(高原橫跨 b 0.5~0.75)。

**方法誠實揭露**:調參與評測用同一份 100 題(無 held-out)——數字有過擬合風險,
應解讀為「本語料+本題組的上界估計」;dense 對照時兩邊都用各自調參後最佳值才公平。
### 2.3 dense(bge-m3)首組數字(2026-09-14,4090)— 採樣偏差抽驗已完成,可引用

bge-m3(`BAAI/bge-m3` @ 5617a9f6,sentence-transformers 5.7.0,cosine,離線建索引 8029 筆 40 秒),
100 題,與 BM25 同一 eval set、同一脈絡欄位規則(`index_text` 共用):

| 配置(eval set **v1.1**,hash 859b0d7a,127 真值) | recall@1 | recall@10 | hit@10 | MRR |
|---|---|---|---|---|
| BM25 純正文調參(k1=0.5/b=0.1) | 0.626 | 0.870 | 0.900 | 0.777 |
| BM25 +脈絡調參(k1=0.7/b=0.5) | 0.666 | 0.905 | 0.920 | **0.808** |
| bge-m3 純正文(未調參) | 0.624 | 0.887 | 0.910 | 0.780 |
| bge-m3 +脈絡(未調參) | 0.589 | **0.906** | 0.920 | 0.761 |

(v1 → v1.1 的差異在 0.01 內:新補的 4 筆真值兩邊 top-10 都沒取回,只讓分母變大;
v1 時 dense +脈絡 recall@10 為 0.911,BM25 +脈絡調參為 0.905。§2.1、§2.2 仍為 v1 數字。)

**發現 5(事實)**:dense 零調參即追平 BM25 調參後水準;+脈絡的 recall@10 全表最高但只多 0.006
(100 題上是 1 題),不構成結論。
**發現 6(事實)**:脈絡欄位對 dense 的作用與 BM25 相反——recall@10 升、recall@1 與 MRR 降。
判斷(待驗證):標題文字混進 embedding 稀釋正文語意,傷 top-1;BM25 是詞項加權不會被稀釋。
**方法誠實揭露**:eval set 真值以 BM25 多輪改寫窮舉建立(§10 2026-08-31),dense 命中而 BM25
未命中的 chunk 可能是漏標真值。**抽驗結果(2026-09-14,`tools/audit_dense_hits.py` + 人工判定)**:
dense 全未命中的 16 題其 top-5 候選 97 筆、已命中題中 dense 獨有前 2 名候選 69 筆,**166 筆全數判「否」**——
BM25 建立的真值沒有可被 dense 偵測到的採樣偏差,dense 獨有的結果全是錯的;eval set 維持 v1,不重跑。
**反向抽驗(2026-09-14,第一批 25 題)**:逐題列出真值所在文件的全部 chunk(大文件取真值 ±8),
474 列、人工判 439 列 → **4 筆漏標真值 + 1 筆跨題漏標**(全為「同一事實在語料多處出現」;其中 3 筆是
前幾批因摘錄截斷 160 字而誤判否,全文一出即翻案)。正向抽驗(top-5)確實看不見它們——盲區實證。
處置:補進 eval set 凍結為 v1.1 並重跑全部設定(見 §10 2026-09-14);其餘 75 題的反向抽驗列入待辦。
**副發現:標題路徑帶著答案**——兩處真值的正文破碎或無答案,heading_path 才是乾淨答案。
這表示 ctx 與 plain 的差距有一部分不是 embedding 或詞項的差距,而是「標題路徑有沒有被算進索引」;
後續 ablation 解讀 ctx 增益時要把這一項分開。

**發現 7:dense 在本語料的失敗模式高度集中(抽驗副產品,比主結論更有用)**——
1. **藥名盲、句型命中**(最大宗):半衰期、儲存條件、副作用表等仿單段落高度同構,dense 學到段落長相
   但不把藥名當硬約束(Cephalexin 半衰期 → 前四名是四種別的藥的半衰期段落)。對策方向:hybrid + rerank
2. **相鄰切塊差一格**(7 筆):落點正確、chunk 邊界切在答案前後一塊。這是 chunking 問題不是 embedding 問題,
   overlap / parent-child retrieval 應可直接吃掉;最便宜的改善
3. **同語意場、錯文件**:認得「語言治療項目」但分不出是支付標準 44xxx 還是復健病房 PACST
4. **整題崩壞**(3 題):兩組 top-5 無一沾邊;其中 1 題只在 ctx 組崩,疑為 doc_title 前綴把大文件語意帶進去
另有同形字誤命中(「疱」)、「早熟 vs 早產兒」。
干擾項增補:3 筆鄰近代碼型 + 7 筆相鄰切塊型進 `data/eval/hard_negatives.json`(共 41 筆),
前者供 reranker 評測、後者供 chunking ablation。這四類失敗模式即 A 軸後續 ablation 的切入點。

### 2.4 chunking ablation:檢索期鄰塊擴展(2026-09-14)— 結論:在 k 預算鎖死下兩邊都退步

針對發現 7 第 2 類(相鄰切塊差一格,7 筆)。真值是 chunk 內文 hash,重新切塊會讓真值全失效,
故對策放在檢索期:`NeighborExpand`——命中後插入同文件 ±window 鄰塊,去重後**截回 top_k**
(base 也只看 top_k,k 預算與對照組相同)。window=0 即對照組。

| 配置(v1.1) | window | recall@3 | recall@5 | recall@10 | MRR |
|---|---|---|---|---|---|
| BM25 +脈絡調參 | 0 | **0.808** | **0.854** | **0.905** | **0.808** |
| | 1 | 0.711 | 0.796 | 0.884 | 0.791 |
| | 2 | 0.711 | 0.736 | 0.839 | 0.782 |
| bge-m3 +脈絡 | 0 | **0.810** | **0.854** | **0.906** | **0.761** |
| | 1 | 0.684 | 0.765 | 0.868 | 0.734 |
| | 2 | 0.679 | 0.739 | 0.830 | 0.727 |

**發現 8(事實)**:鄰塊擴展在固定 k 預算下讓 BM25 與 dense 全面退步,window 越大越差;
recall@1 不變(第一名永遠是原命中)。**判斷**:擴展把原本第 2~5 名的真值擠出榜外,
損失遠大於 7 筆相鄰漏檢的收益(dense 那 7 筆最多換回 hit@10 +0.07,實測 hit@10 反降 0.02)。
pre-mortem 預言的「k 預算」機制成立,只是方向與預期相反。
**否決此對策**;若要再試,只剩兩個變體:①只擴展前 m 名(m=1~2)、②鄰塊放榜尾不插隊——
兩者都是在同一 k 預算下少犧牲原命中,但收益上限仍是那 7 筆,優先序低於 hybrid + rerank。
方法揭露:`tools/gauntlet.sh` 5d 每次重跑六組 BM25(含 w1/w2),雲端可重現;dense 兩組在桌機。

### 2.5 hybrid(RRF 名次融合)— 首組數字(2026-09-14,4090,v1.1)

base = BM25 +脈絡調參 與 bge-m3 +脈絡(各家族最佳組);`HybridRRF`:每邊取 pool 筆 → RRF 融合 → 截回 top_k。
**先算聯集上限**(pre-mortem 要求:融合增益必須超過「單邊放大池」):

| 深度 N | BM25 recall@N | bge-m3 recall@N | 兩邊 top-N 聯集 recall | 聯集 hit |
|---|---|---|---|---|
| 10 | 0.905 | 0.906 | **0.975** | 0.98 |
| 20 | 0.938 | 0.958 | 0.975 | 0.98 |
| 40 | 0.968 | 0.980 | 0.985 | 0.99 |

**發現 9(事實)**:兩邊 top-10 的聯集 recall 0.975,比任一單邊高 0.07——兩個檢索器漏的題目幾乎不重疊,
這是 hybrid 的全部理論空間;深度加到 40 只再多 0.01。

網格 pool ∈ {10, 20, 40} × rrf_k ∈ {10, 60, 100},輸出固定 top_k=10:

| pool | rrf_k | recall@3 | recall@10 | hit@10 | MRR |
|---|---|---|---|---|---|
| 10 | 10 / 60 / 100 | 0.855 | **0.965** | **0.97** | 0.836 |
| 20 | 60 | 0.865 | 0.951 | 0.96 | 0.838 |
| 40 | 60 | 0.875 | 0.951 | 0.97 | **0.840** |

**發現 10(事實)**:rrf_k 三格數字幾乎相同(高原);pool 是主變因,且 pool=10 的 recall@10 最高,
放大 pool 反而降 0.014,但 recall@3 / MRR 隨 pool 略升。**判斷**:pool 放大後「兩邊都中等」的 chunk
靠兩票累加壓過「一邊第 1、另一邊未進池」的真值;小 pool 等於要求另一邊也排進前段才給第二票。
**pre-mortem 檢核通過**:hybrid 在 k=10 預算下 0.965,高於單邊看 20 筆的 recall@20(0.958),增益不是「看更多」。
pool 細格(8 / 10 / 12 / 15,rrf_k=60):recall@10 0.963 / 0.965 / 0.963 / 0.963,MRR 0.837 / 0.836 / 0.837 / 0.839,
recall@3 0.842 / 0.855 / 0.855 / 0.865——8~15 為高原。**代表點取高原中點 pool=12、rrf_k=60**
(`configs/hybrid_rrf_full100.yaml`):recall@3 0.855 / recall@10 0.963 / hit@10 0.97 / MRR 0.837。
**發現 11(事實)**:對最佳單邊,hybrid 讓 recall@10 +0.057、recall@3 +0.045、MRR +0.029(對 BM25)——
A 軸目前最大單項增益;它吃掉的正是發現 7 的「藥名盲」與「同語意場」:BM25 的詞項約束補上 dense 缺的實體敏感度。
方法揭露:網格與代表點都用同一份 100 題,無 held-out,數字為上界估計;pool 的高原寬(8~15)降低了過擬合疑慮。

### 2.6 reranker(bge-reranker-v2-m3 cross-encoder)— 首組數字(2026-09-14,4090,v1.1)

base = hybrid 代表點(pool=12、rrf_k=60);`RerankRetriever`:base 取 candidates 筆 → cross-encoder 打分 → 截回 top_k=10。
模型 `BAAI/bge-reranker-v2-m3 @ 953dc6f6`,零調參;重排文本兩種:plain(正文)與 ctx(正文 + doc_title,與索引端同規則)。
網格 candidates ∈ {10, 20, 30} × {plain, ctx};另以 42 筆 hard negatives(相鄰切塊 / 同語意場錯文件)做「真值最高分 > 干擾項分數」檢核:

| candidates | 文本 | recall@3 | recall@10 | hit@10 | MRR | ms/題* |
|---|---|---|---|---|---|---|
| 10 | plain / ctx | 0.941 / 0.943 | 0.963 / 0.963 | 0.97 | 0.903 / 0.920 | 143 / 146 |
| 20 | plain / ctx | 0.936 / 0.943 | 0.971 / **0.975** | 0.98 | 0.898 / **0.921** | 256 / 262 |
| 30 | plain / ctx | 0.936 / 0.943 | 0.961 / 0.965 | 0.97 | 0.897 / 0.920 | 263 / 269 |

\* 每題全鏈耗時(BM25 + dense + rerank,含 base),非純 reranker 開銷;§5.4 效能量測時另拆。
hard negatives:plain 真值勝 38/42 = 0.90、ctx 39/42 = 0.93。

**發現 12(事實)**:對 hybrid 代表點,reranker 讓 recall@3 0.855 → 0.943(+0.088)、MRR 0.837 → 0.921(+0.084),
recall@10 0.963 → 0.975(+0.012)——A 軸目前最大的**頭部**增益;hybrid 已把真值撈進前 20,reranker 負責把它推到前 3。

| 配置 | 每題平均 | 對 BM25 倍數 |
|---|---|---|
| BM25 +脈絡調參 | **13.4 ms** | 1× |

且與 vLLM 共用同一張 4090**(`--gpu-memory-utilization 0.75`,伺服端同時在跑);
上表為 §2.6 rerank grid 路徑的粗估。**我的判斷(未做對照實驗)**:差距主要來自 bge-m3 查詢向量與 cross-encoder

**這個數字的用途**:它是**單卡同機部署**(檢索與生成共用一張卡)的實際體感延遲,
也就是 demo 的真實條件。推薦配置換到 recall@10 +0.07、recall@3 +0.13 的代價,在這個條件下是每題多約 1.5 秒。
若檢索與生成分卡、或查詢可批次,此數字會大幅下降(未量測)。
† 為 v1.1 數字(未在 v1.2 重跑);四個代表點 v1.1 → v1.2 差異全部 ≤ 0.003,方向一致(新增 2 筆真值皆未進 top-10,只放大分母)。

**決策**:推薦 **hybrid(BM25 +脈絡 ⊕ bge-m3 +脈絡,RRF pool=12)+ bge-reranker-v2-m3 重排前 20 筆、文本含 doc_title**。
理由是兩段增益來源不同且可疊加:hybrid 補「有沒有撈到」(recall@10 +0.057,兩檢索器漏檢幾乎不重疊),
reranker 補「排在前面」(recall@3 +0.088、MRR +0.084);合計 recall@10 0.903 → 0.973、recall@3 0.808 → 0.941(v1.2)。

**最無聊但最穩:BM25 +脈絡調參**。零 GPU、純標準庫、建索引 1 秒、查詢 1 ms,recall@10 0.905 已在推薦配置的 0.07 以內;
若部署端沒有 GPU 或需求只是「答案在前 10 筆就好」,這是正確答案,dense 單獨上並不比它強(0.906 vs 0.905)。

**要不要上向量庫?** 單獨用 dense 沒有理由(對 BM25 +0.001);理由只在 hybrid——向量索引是為了和 BM25 互補,不是取代它。
8029 筆的規模 `.npz` 全載入記憶體即可,獨立向量庫在本規模不是必要元件(規模 >10⁶ 時另議)。

**reranker 值不值得?** 值得,前提是頭部指標重要(生成期只餵前 3~5 筆時,recall@3 就是命中率);
代價是查詢期 GPU 與延遲——§2.6 路徑粗估每題 +230 ms,但**單卡與生成共用時 demo 實測為 13.4 ms → 1501 ms(×112)**,
上線前必須在自己的部署條件下重量一次,不能直接引用任一數字。NIM 是同級替代,快約 18%、recall@3 低 0.017,適合延遲優先且已有 NGC 基礎設施的環境。

**被否決的方案**:鄰塊擴展(§2.4:k 預算下兩邊退步);分數加權融合(需正規化與 α,歸因混雜);
heading_path 單獨入索引(§7 第 1 條);dense 單獨上(增益 0.001)。

**適用邊界(誠實揭露)**:①全部數字為同一 100 題上的上界估計,無 held-out;②語料為中文政府公開文件,
藥名英文夾雜是主要失敗模式來源,其他領域的 BM25/dense 相對強弱可能不同;③延遲有兩組數字、條件不同:上表 260 ms 為粗估且含不同呼叫路徑,demo 實測 1501 ms 為單題不批次且與 vLLM 共卡,
兩者皆非「獨占 GPU + 批次」下的值;
④reranker 兩模型精度不同(FP8 vs FP16),未做同精度對照;⑤真值集為 AI 出題 + 人工判定,反向抽驗僅完成第 1 批。

## 4. C 軸:量化格式(AWQ / GPTQ / FP8)

### 4.0 前置閘門(2026-09-17)

- 格式來源:AWQ / GPTQ 用 Qwen 官方預量化 checkpoint(校正資料為 Qwen 所用,與本專案 FP8 的 512 筆語料校正不同,每張表標明);FP8 用 §3 的 ModelOpt checkpoint。
- **閘 C-1(事實)**:`trtllm-serve serve Qwen/Qwen2.5-7B-Instruct-AWQ` 載入失敗——PyTorch 後端 `load_weights_fused_gate_up_helper`
  斷言每層有 `weight`,AutoAWQ checkpoint 只有 `qweight / qzeros / scales`。TRT-LLM × AWQ(HF 格式)= N/A;
  這是立案假設「格式與引擎綁定」的第一個實證:同一個 AWQ 權重檔在 vLLM 可跑(§首日驗證 2),在 TRT-LLM 不能。
  TRT-LLM 的 AWQ 正路是 ModelOpt 自行量化匯出(未做,列 C 軸待辦)。

## 6.6 demo 引用層人工複核(2026-09-19)— 逐字覆蓋率不能當 support 的代理

demo prompt v13_cite 要求每句標 `[段落編號]`,確定性層核對「有效 / 越界 / 是否引到真值」,並算每句
「字元 3-gram 被**所引段落**覆蓋的比例」。100 題 × 2 preset:引用遵循率 100%、零越界;
覆蓋率 < 0.5 的引用句佔 0.321(BM25)/ 0.345(hybrid)。
以 40 題 × 2 preset(74 條有引用句)取出全部 23 條低覆蓋句人工逐條判型:

| 判定 | 筆數 | 說明 |
|---|---|---|
| 改寫(內容有據、措辭不同) | 12 | 低覆蓋的多數,不是錯誤 |
| 編造(所引段落無此內容) | 11 | 見下方子型 |
| 跨段落綜合 | **0** | 引用多段的 5 筆皆為「內容全來自其中一段」,引用清單有裝飾成分 |

**發現 28(事實)**:**逐字覆蓋率不能當 support 的代理指標**。三個反例足以推翻:覆蓋率 0 的一筆是逐字忠實的改寫;
覆蓋率 0.351 的一筆是**錯藥命中**(問 Metronidazole 神經系統警語,引到止瀉藥仿單的「疲勞、眩暈或昏睡」);
覆蓋率 0.484 的一筆是**因果倒置**(語料「因本品降血糖作用甚強,故須餐時服用」→ 句子「因為此時藥物的降血糖作用最強」)。
因此本專案將覆蓋率定位為**診斷旗標**(排序「哪句需人工查證」),**禁止進入任何分數或配置比較**;
程式與 UI 措辭同步改為「需查證的引用句 a/b(診斷旗標,非品質分數)」。

**11 筆編造的六種子型**(依危險程度):①錯藥命中(逐字命中但來自別的藥,最難以人工快掃發現);
②因果倒置(字面幾乎全中,錯的只有因果方向);③相鄰條文誤歸(給付限制取到下一個藥品的尾句,與反向抽驗同型);
④**引用錯置 4 筆**(內容正確但引錯段落——同一句在另一 preset 引對就完全有據,嚴格說不是幻覺,
**獨立成類以免高估幻覺率**);⑤單位錯置(「每次 2 粒」→「每日 2 粒」,日劑量差 4 倍,與 judge 校準集同型);
⑥表格殘片誤讀(欄位編號被當成給付項目)。

**高覆蓋帶補抽(2026-09-20,爭議 2)**:從覆蓋率 ≥ 0.5 的引用句抽 20 條(GPTQ、同兩 preset、seed 42)
人工判型 → **改寫 19 / 綜合 0 / 編造 1(0.050,Wilson 95% [0.009, 0.236])**。兩帶覆蓋率完全不重疊
(低帶 0–0.489、高帶 0.541–1.000),分層乾淨。分層加權後:

| 帶 | 句數 | 判定方式 | 編造率 |
|---|---|---|---|
| 覆蓋率 < 0.5 | 23 | 全量 | 0.478 (11/23) |
| 覆蓋率 ≥ 0.5 | 51 | 抽 20 | 0.050 (1/20) |
| **加權估計** | 74 | — | **0.183,區間 [0.155, 0.311]** |

(區間只傳遞高帶的抽樣不確定性;低帶是全量計數,無抽樣誤差。)
**這個估計有一個條件必須寫明**:高帶抽樣落在 18 題上,與低帶 23 句所在的 18 題**只有 5 題重疊**
(`b1-q04`、`b1-q19`、`b1-q22`、`b2-q05`、`b2-q11`),高帶獨有的 13 題含較多支付標準單值題(`b1-q21`、`b1-q23`、`b2-q02`),
題目難度較低。因此 0.050 對「同一批 51 句」可能偏低,加權估計 0.183 應讀作**點估計而非無偏估計**;
可確定的是 **11/74 ≈ 0.149 這個下界已被推進為約 0.18,且高覆蓋帶確實不是無錯區**(仍抓到 1 筆)。

**適用邊界(必讀)**:兩個 preset 的編造數相當(5/5 vs 7/6),
**hybrid 沒有比較好**:檢索改善不會自動改善生成忠實度。
另記一筆不屬於 support 的缺陷:一句把 methotrexate 譯成不存在的藥名(正解甲氨蝶呤),同批其他中譯正確,判為單次生成失誤,
但在醫藥場景嚴重度不低於編造,列為「藥名譯寫」獨立觀察項。

**兩組內部對照**(retrieval 差異直接導致 generation 錯誤的乾淨案例):同題 b1-q11,BM25 撈到相鄰條文並誤歸、
hybrid 撈到正確條文;同句不同 preset(b2-q01)引用編號一錯一對。

**處置**:①覆蓋率降為診斷旗標(已落地);②引用錯置獨立成類,不計入幻覺;③「引用是否**語意上**支持該句」
仍是 judge 第二階段的工作,本層只做確定性格式檢查;④六種子型併入 judge 第二階段的錯型清單;
⑤覆蓋率的篩選閾值收斂為「< 0.1 優先人工看」——爭議 3 的雙向反證(見 §6.7)顯示對「引用相鄰但誤歸」無效,
0.5 這個門檻只適合當 UI 旗標,不適合當人工複核的排序依據。

## 6.9 成分判定第二輪(2026-09-21)— 同輸入只換判定層,把「修好了」從推測變成實證

第一輪暴露 5 筆假漏判與一個設計矛盾,修完後以**完全相同的設定**重跑
(GPTQ-Int4、seed 42、同語料、同 preset)。

**發現 36(事實):兩輪的模型輸出逐字相同,因果乾淨**。程式比對 172 列的
`preset / item_id / 句子 / 引用編號 / 覆蓋率 / 所引段落` 六個共用欄位,**零差異**。
因此判定欄沿用第一輪(改寫 142 / 綜合 2 / 編造 28),而成分欄的每一筆變化
都**只能**歸因於判定層。這個實驗設計比數字本身更值得記:**要歸因於某一層的改動,
就得讓其他層的輸出逐字可比**——否則「修好了」與「模型這次剛好答對」分不開。

| 驗證項 | 結果 |
|---|---|
| 5 筆假漏判 | **全部修復**(`b1-q22` 特材、`b3-q05` 24 小時上限 ×2、`b3-q19` 支付點數 ×2) |
| 反向退步 | **零筆**從命中變缺漏、**零筆**新增錯誤命中(30 列有成分的列全查) |
| 裸數字別名誤傷 | 無(`b4-q15` 的 `650` 仍命中,且所引段落確實含「發現費650點」) |
| `b1-q19` 的矛盾 | 標出**三項**而非預期的兩項——被引句「補助對象每二年進行一次檢查」
  同樣沒有「45-74 歲」,四個成分只有「頻率」有引用支撐 |

**發現 37(事實):單一「引用支撐」欄有結構性盲點,補成兩欄才蓋得住引用錯置**。
第一版欄位檢查的是「成分是否出現在**有引用標記的句子**裡」,所以抓得到
「成分只在未引用句」(`b1-q19`),卻抓不到「句子有引用、但**所引段落**不含該成分」——
而後者正是 §6.8 發現 32 的 10 筆引用錯置。實證兩例:`b3-q12` 的建議劑量與注射間隔
兩成分全中、欄位為空,但所引 `[3]` 是血友病劑量表根本不含 `10-40 IU/Kg`;`b2-q04` 同型。
處置:拆成互斥兩欄——

| 欄 | 語意 | 對應的 support 錯型 |
|---|---|---|
| 命中但**未引用** | 成分只出現在沒有引用標記的句子 | completeness 與 support 的母體差異 |
| 命中但**引用不支撐** | 成分在引用句裡,但所引段落不含它 | **引用錯置** |

互斥由「已在未引用欄的不再進引用不支撐欄」保證,避免同一成分被兩欄重複計。
兩者用同一個比對函式,只換比對對象(引用句 → 所引段落)。

**判定層的三條規則至此成形**(皆由跑分暴露、非事前設計):
①**數字邊界**——別名邊緣是數字時,答案中相鄰字元不得是數字。`b3-q19` 的
「支付點數為1500,」用別名修不好(`點數為1500` 會誤中 `點數為15000`),必須在判定層解決;
規則生效後三處支付點數的別名改回裸數字反而**涵蓋更多語序且清單更簡單**。
②**字形正規化到位、語意正規化禁止**(§6.6 的 N4)。
③**兩種「無支撐」分欄**(發現 37)。

**仍未量到的**:引用錯置那一型的實際筆數要等第三輪(新欄位首次帶著真模型跑)。
前兩輪已證明輸出穩定,所以第三輪的差異同樣會是純判定層效果。
(第三輪結果見 §6.10。)

**引用錯置的計數口徑**(兩種都對,別混用):**純引用錯置 10 筆**(內容正確、只標錯編號)
是發現 32 的分子,`b2-q04` 因同時有四倍劑量的單位錯置被歸入實質錯誤而不計;
若改問「有幾筆的引用標號指向不含該內容的段落」,答案是 **11 筆**(含 `b2-q04`)。
新欄位量到的是後者這一型,所以它在 `b2-q04` 標出是正確行為,不是與發現 32 矛盾。

(第三輪的「甲基軹酸酯」在本輪完全沒命中,換個錯法就漏),而 prompt 只能規範「要不要翻」,
規範不了「字寫錯」。**處置:藥名一路改走後處理層**(把句中藥名對照被引段落,不在段落裡的標記),
不依賴模型遵守規則;這同時移除 v14 中沒有效果卻貢獻了 65 字 system 長度的那一條。
**反向誤傷經程式掃全部 178 句確認為零**:句中有、所引段落沒有的英文詞全部來自題目,

**無法分辨**,成分完整率的 -4 因此無法定案。第一次是發現 37 的母體差異,同一根因。
處置:`--dump-answers` 把每個 (preset, item) 的完整回答寫成 jsonl,**與是否產生列無關**,

**棄答本身會錯,而且錯得不少**:21 筆棄答裡**至少 11 筆的真值 chunk 就在取回結果內**,
有的排第一、甚至模型標的引用編號正指著那一塊(`b4-q21` bm25 的 01040C 點數、

而所引 `[1]` 明寫「每一個案每一院所支付以一次為限」。這與「格式槽位缺料時 LLM 會升級材料充填」的既有觀察是**同一機制的反向**:那裡是「假稱存在」,這裡是「宣稱缺席」。
成對規則的另一半(禁宣稱缺席)在本專案的 demo prompt 裡還沒寫。

**是錯的**。本輪 `r174` 引到附件二,原文即「可參用23週以內之院外CT、MRI或腹部超音波檢查結果」,

## 6.13 第六輪:新基準(2026-09-22)— 棄答首次進表,dump 一輪抓出三個表格層缺陷

**這是新基準**,前五輪的編造率分母不可與它比較(2026-09-22 核准不補標前五輪)。
206 列 = 185 作答 + 21 棄答。prompt 仍 v15_noprefix,只換表格。

**發現 49(事實):「同一組輸出、只換表格」以雙向比對確立**。185 列作答句逐句剝除引用標記
後對 jsonl 回答比對,**0 列對不上**;jsonl 本身與第五輪 200 筆**零差異**。
後續三項驗收因此可歸因於表格層,與模型無關。

**發現 50(事實):反向驗收成立——「外來詞」欄 0 列,與人工重算一致**。
這一欄的驗收刻意設計成反向:v14 曾掃全部 178 句確認「句中有、段落沒有」的英文詞**全部來自題目**,
所以題目列為合法來源後這欄應接近全空。人工用 jsonl 對段落與題目重算得 0 列,與表格一致。
**「欄位沒訊號」與「欄位壞了」因此可以分辨**——這個設計比正向驗收有用。

**發現 51(事實):錯誤棄答定案 11/21,且多數引的正是含答案的那一段**。
21 筆棄答中 11 筆有真值名次,人工逐筆確認**全部是錯誤棄答**(真值段落確實含答案);
其餘 10 筆真值未取回,屬檢索失敗而非生成失敗。這一整類過去不在任何分母裡(發現 47)。
**2026-09-29 排除檢查**:11 筆的真值 chunk 與「heading_path 含 >40 字正文誤判」的 7 題(`data/corpus/SOURCES.md` 已知抽取缺陷)零重疊,
所以不是答案藏在 heading、模型看不到;錯誤棄答仍歸生成端。

**發現 52(事實):`--dump-answers` 在第一輪就抓出三個表格層缺陷,兩個是「函式對了、呼叫點錯了」**。
沒有 jsonl,這三個都不可見:

| 缺陷 | 根因 | 影響 |
|---|---|---|
| **混合型不可見** | `if not sups` 才產生額外列。`b4-q15` hybrid 是「第一句有引用 + 第二句宣稱缺席」,sups 非空故永不觸發 | 發現 48 那一型在表上仍然看不到 |
| **棄答列丟掉引用編號** | 棄答列的引用欄寫死 `""` | 22 筆含棄答字樣者有 **21 筆帶 `[n]`**;「引了段落卻說沒提到」這個強訊號整批遺失 |
| ~~名次算錯~~ | **不成立**,見下 | — |

前兩個同型:**`is_abstain` 判「含」而非「等於」正是為了混合型,函式層做對了,呼叫點用 `if not sups`
把它擋在外面**。對應的 property 守住了函式的語意,守不住呼叫點——**不變量的作用域就是它被呼叫的地方**,
這是本次最值得記的一條。

**更正一則(2026-09-22,查證推翻)**:人工報告「`b1-q24` 名次應為 1 而非 2,因為該題有兩個真值」。
查 eval set v1.2:`b1-q24` 的 `relevant_doc_ids` **只有 `#0000` 一筆**,而 bm25 把 `#0001` 排第 1、
`#0000` 排第 2,所以 `truth_rank` 回 2 是正確的。`#0001`(出題來源公告頁)是否該算真值屬**領域認定**,
若要收入就得動 eval set(v1.3、換 hash、重跑 A 軸代表點),不是這一欄的缺陷。
**這一欄的正確語意是「eval set 所記真值的最小名次」**,其準確度上限即 eval set 真值的完整度。

**已入冊的限制**:「段落有但未照抄」欄在真語料上 **141 列有值**,誤報率高到不具篩選力
(段落列多個藥名、句子只答其中一項就會標)。它對 `b2-q11` 那型(英文藥名被寫成中文亂碼)有效,
但要人工先過濾掉大部分噪音;**不得進入任何分數,也不宜當排序依據**。

**混合型列刻意不做(2026-09-23 核准)**:發現 52 的第一個缺陷——「第一句有引用 + 第二句宣稱缺席」
在表上仍不可見——**評估後決定不修**。理由是回報率:實測只有 **1 筆**(`b4-q15` hybrid),
而 `--dump-answers` 已經讓它可見(人工正是用 jsonl 發現它的),表格加列只是把已可見的東西
再呈現一次;成本卻要切句邏輯(`core` 的私有函式跨層 import、或重寫第二份、或改公開 API 破壞
「不改 core」的約束)加上一輪 100 分鐘的 gauntlet。第二個缺陷(棄答列的引用編號)反而修了,
因為它遮住 21 筆且不需切句。**同一份修正規格裡的兩個缺陷性價比差一個數量級,綁在一起問是錯的**。
再評估的觸發條件:若日後加入「禁宣稱缺席」規則使混合型筆數上升,屆時再做。

## 6.14 真值判準顯式化(2026-09-23)— `b1-q24` 的 `#0001` 不收,判準寫死為「text 含答案」

第六輪人工報告主張「`b1-q24` 有兩個真值,名次應為 1」;查證推翻了名次的部分(§6.13 更正),
但留下真問題:`#0001` 該不該補進真值。驗證走四步(決策 5 建置流程的單題重放):
①題目化約成答案要素(收件截止日=一個日期字串)②候選塊的 `text` 與 `heading_path` **分開**檢視
③判準:text 含答案才算等價塊 ④grep 全語料等價表述確認沒有第三塊。

**發現 53(事實):`#0001` 的答案只在 heading_path,text 是聯絡方式與檔案下載**。
全語料掃描:「115-09-01」text 只在 `#0000`;「115年9月1日」text 另出現兩塊,
但分別是**藥品查檢表的修訂日**與**牙醫方案的生效日**——巧合同日、不同事件,是天然 hard negative。
所以在「text 含答案」判準下,這題**零漏收**,`truth_rank` 的 2 正確,什麼都不用重跑。

**判定(2026-09-23 拍板):不收 `#0001`,判準顯式化為「真值塊 = text 含答案(可獨立作答)」**。
被否決的替代判準是「檢索層等價」(heading 有入 BM25 context_fields,檢索器憑答案字串找到它):
否決理由是 recall 的存在意義是預測「生成拿得到答案」,而 `make_messages` 只送 text——
模型拿到 `#0001` 答不出日期。收它會讓檢索分數與端到端表現脫鉤,
且等於用真值集吸收 chunking 的傷(答案被切進標題=斷頭 chunk 的另一面向,誠實區第 9 項),
掩蓋 A 軸 parent-child 待辦的價值。**病灶在 chunking,修法也在 chunking,不在標註。**

**方法論沉澱**:此判準是決策 5 一直隱含的前提,本例逼著寫明。日後任何「這塊算不算真值」的
爭議都先走上述四步;第②步的「text 與 heading 分開看」是關鍵——兩者在檢索層被混在同一個索引裡,
在生成層卻只有 text 存在,混著看必然誤判。

**發現 55(判斷,證據強):對 7B 量化模型,這類 meta 檢查指令的實際作用是字串促發,不是行為檢查**。

與 v14 教訓合併,demo prompt 的可行改動空間收斂到:**只能加「格式/句式」約束(禁前言成功),
不能加「要求模型自我檢查」的 meta 約束(藥名照抄失敗、禁宣稱缺席反效果)**。

**處置**:①`configs/demo.yaml` 整句回退 v15(輸出行為 = 第六輪,無需重跑驗證輪)
②錯誤棄答的守門**放棄 prompt 層,定案走確定性層**——support 表的棄答列 + 真值名次欄

列為已知限制,如實陳述 ③混合型筆數 run7 = 3(run6 = 2),未達再評估門檻,不修決定維持。

**預期管理的失敗紀錄**:動工前的預期是「錯誤棄答下降、不預期歸零」,實際方向完全相反。
錯在把「規則能收斂裁量」(對輸出**格式**成立的既有經驗)外推到「規則能新增檢查行為」——
後者對這個規模的模型不成立,而且事前沒有任何一輪數據支持這個外推。

   本語料 chunk 長度已被切塊參數約束,長度正規化反而懲罰含完整條文的長 chunk;
   中文 bigram 的詞頻雜訊偏好低 k1。教訓:baseline 的「預設值」也是一個未經驗證的假設。
3. **「三條 property 不變量足以鎖住 hit@k」——變異測試證明不夠**(2026-09-01)。
   ≥recall、單調、值域全是單邊界限,「永遠回報命中」的錯誤實作全數通過;
   對 property 子集單獨重跑變異才揭露。修正:補雙邊鎖定 hit == (recall > 0)。方法論層級的教訓:
   一側界限要配對另一側。
4. **「NIM 在 WSL2 上跑不起來」——第一個時間盒的停損判定被第二個時間盒推翻**(2026-09-15)。
   閘 2 容器啟動即 `CUDA failed to initialize [[ Named symbol not found (error 500) ]]`,TRT segfault;
   一次「移除 /usr/local/cuda/compat」的修復無效,兩小時到,判定為「WSL2 + Docker Desktop 環境層問題」停損入冊。
   追加一小時時間盒後,第一個動作「更新 Docker Desktop」(Engine 24.0.7 → 29.8.0)就直接修好,同一指令服務就緒。
   教訓:停損判定把「宿主環境不支援」與「宿主軟體太舊」混為一談;版本檢查成本最低,應是任何容器 GPU 問題的第一嫌疑。
   NGC 支援矩陣 23 個 profile 無 GeForce,但 4090 靠 sm_89 相容直接用 L40S 引擎,「不在支援矩陣」不等於跑不動。
5. **「NV-Embed-v2 可與 bge-m3 並列對照」——在釘選的 transformers 4.57.6 下載入失敗,放棄**(2026-09-15)。
   模型(remote code @ 3fa59658)下載與權重載入正常(fp16,4 shards),推論即崩:第一點
   `DynamicCache.get_usable_length` 已改名,以 shim 補回;第二點 remote code 自寫的 decoder 迴圈未傳
   `position_embeddings`,transformers ≥ 4.48 的 Mistral attention 改由上層計算 rotary 後傳入,
   `cos, sin = position_embeddings` 解包 None。修這點要改模型檔;降版 transformers 則與 vLLM 0.22.1 綁定的
   4.57 衝突,另開第三個 venv 只為一個對照組不值得。另一個實際代價:NIM reranker 常駐時佔 18.5 GB VRAM
   (Triton workspace),與 7B 生成模型無法共存,bge-reranker 進程內約 2 GB。
   結論:A 軸 embedding 維持 bge-m3 單測;NV 訊號由 NIM reranker 對照(§2.6)承擔。
   教訓:`trust_remote_code` 模型的相容性由「模型檔的 transformers 版本」決定,與釘選無關,首日驗證要排在釘選前。
6. **「TensorRT-LLM 在 4090 上會明顯快過 vLLM」——bf16 下輸了,FP8 下只贏 6%**(2026-09-15)。
   立案時把 B 軸當 NVIDIA 敘事主軸,預期引擎差距是主要變因;實測三個併發等級 bf16 差距 ≤ 10% 且 vLLM 略勝,
   FP8 才讓 TRT-LLM 反超 6%,而 FP8 本身帶來 ×1.4–1.7。真正的變因是數值格式,不是引擎;
   4096 上下文、45 tokens 短回答、併發 ≤ 8 的負載也遠未讓兩者的排程器差異顯現。
   另一個沒料到的:FP8 讓近半數 greedy 輸出改變(§3.2 發現 20),「速度表」若不配品質表會誤導。
- (隨後續實驗回填)
7. **「FP8 是 Ada 上的最佳格式」——被 W4A16 以 ×1.6 再超車**(2026-09-17)。B 軸把 FP8 當終點(×1.4),
   C 軸一跑官方 AWQ / GPTQ,c=8 吞吐 1000 tok/s 對 FP8 610;且 GPTQ 的 faithfulness 0.960 與 bf16 在 judge 下不可分辨。
   當初假設「4-bit 品質代價一定比 8-bit 大」,judge 沒看到;看到的只是「逐字更不像 bf16」(一致率 0.25 vs 0.51),
   兩者不是同一件事——這是本專案第二次「輸出改變 ≠ 品質下降」(第一次是 §3.2 發現 20 對 §3.3 品質補列)。
8. **「再加四條明文規則就能修 judge」——零槓桿**(2026-09-18)。分層校準集把 v2 的 κ 從 0.845 打回 0.488 後,
   v3 針對九筆錯型各寫一條規則,重跑 42 筆判定一筆未變。教訓:規則能補「沒查」,補不了「查了判反」;
   後者要換結構(拆成子問題)或換模型,不是換措辭。

9. **「heading_path 既然幫了檢索,拿來當生成的脈絡應該也有幫助」——抽驗後放棄,連實驗都沒做**(2026-09-21)。
   首輪成分跑分的引用錯置(10/28)指向一條因果鏈:法規的 `1.` 編號正是標題樣式,
   正文行被 `parse_heading` 誤判為標題 → `chunker.py` 讓標題行只進 `heading_path` 不進 `text`
   → BM25 的 `context_fields` 把它加進索引(**檢索找得到**)→ 但 `make_messages` 只送 `h.text`
   (**模型看不到**)。最直接的修法是把 `heading_path` 併進 context,而且它可逆、不必重建語料。
   **動手前先驗證「路徑品質夠好」這個假設,結果假設被推翻**:抽驗 12 個 chunk 就有硬證據——
   `1 MB`(檔案大小)被當標題、`5 ∼ 10倍之多。`(正文)被當標題、生物標記檢測的路徑配上癲癇藥物條文;
   全語料末層標題與 `text` 的字元 2-gram 重疊率中位數僅 **5.6%**,44.6% 完全無重疊
   (此指標會高估錯配——標題本就比正文抽象——但抽驗的硬證據不受影響)。
   **結論:heading_path 對檢索有用、對生成有害**。檢索只需詞彙重疊(藥名出現在上層標題就夠),
   生成需要語意正確;把 57.5% 低重疊的路徑當脈絡餵進去,是餵「看起來像脈絡」的雜訊,
   而模型會信任它。A 軸的 ctx 增益(0.829→0.905)仍然成立,但那是**詞袋效應**,
   不表示那些路徑適合當脈絡。教訓:同一個欄位在 pipeline 的不同層有不同的品質門檻,
   「在 A 層有用」不能推論「在 B 層也有用」。
   **代價評估**:治本要修 `parse_heading` → 8,029 chunks 重算 → A/B/C 三軸數字全部失效,
   且事前無法知道 recall 會升或降。處置:先只對缺口最大的一份文件試修並量 recall 變化(見 §2.x 待補),
   結果決定要不要付重建的代價。
   **試修實驗已做(2026-09-21,見 `data/corpus/SOURCES.md`)**:對缺口最大的一份文件加
   「標題長度上限 + 句號擋」兩條規則,缺口 32.6% → 10.2% 且被吃掉的正文回到 `text`。
   但閾值極度敏感(`max_len=40` 救得回 `Dravet`、`45` 就救不回)、缺口非單調,
   而且**擋得越多 `heading_path` 越空**——A 軸的 ctx 增益正是靠 heading 進索引。
   要量淨效果必須看 recall,而重算後 `chunk_id` 會變使真值對不上
   → **探路的成本已接近治本的成本**。維持不修,這個數字本身就是代價評估。
   (順帶更正:先前把缺口比例算成 22.3%,分母用了「缺口+覆蓋」而 chunk 有 overlap,
   覆蓋加總會超過全文長度;以 `len(document.text)` 為分母的正確值是 **31.6%**。)
